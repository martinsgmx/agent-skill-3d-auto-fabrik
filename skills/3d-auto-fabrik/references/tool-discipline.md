# Tool discipline — no invented actions

This skill supervises a heated machine. An invented tool call, argument, id
or result can become an unsafe action or a false "it worked" report. Use the
rules below on every job.

## The catalog is the source of truth

The exact tool names, risk tiers, gates and arguments live in the generated
catalogs:

- [mcp-orca-tools.md](mcp-orca-tools.md)
- [mcp-cura-tools.md](mcp-cura-tools.md)
- [mcp-moonraker-tools.md](mcp-moonraker-tools.md)

They are generated by `scripts/generate-tool-reference.py` from
`mcp-orca tools --json`, `mcp-cura tools --json` and
`mcp-moonraker tools --json`. Never hand-edit the tables. Refresh them after a
server upgrade with:

```sh
python3 scripts/generate-tool-reference.py
```

If a name or argument is not in a catalog, do not call it. If a cataloged tool
is not exposed in the current client session, report it as unavailable and
stop that stage. Do not try a near-miss name, and do not use a shell or HTTP
request to imitate a tool the server does not expose.

## Values come from tools or the user, never from imagination

- Tool names, arguments and argument names: copy them exactly from the
  catalog. Do not add well-meaning extra arguments.
- `art_*`, `job_*` and `apr_*` ids, confirmation phrases and expiries: copy
  them from the tool response. Never generate, guess, reuse or paraphrase
  them. A new filename is the only value you may choose; derive it from the
  artifact id and show it to the user.
- Paths, roots, URLs, preset ids and policy limits: read them from live MCP
  facts (`*_policy_info`, `*_server_info`, `*_doctor`, `moonraker_config`) or
  the user's config. Do not assume a client-specific path or an upstream
  endpoint.
- Tool results and numbers: quote the tool output. If a call fails, report
  its own words. Never turn a failure into a plausible success, and never
  fill in a temperature, time, filament length or layer count from memory.

## Every stage needs evidence

| Claim | Required evidence |
| --- | --- |
| Engine usable | doctor's engine entry plus `*_engine_info`, not just overall `ok` |
| Artifact imported | `*_artifact_import` result id and a `*_artifact_get` kind/format check |
| Mesh inspected or repaired | `*_mesh_inspect` numbers before and after |
| Profile resolved | `*_profile_resolve` sources and warnings; Cura `*_profile_verify` with zero errors |
| Sliced | `orca_slice` / `cura_slice` `job_*` id and terminal status |
| G-code reviewed | `*_gcode_inspect` plus header/footer text or `cura_gcode_verify` |
| G-code on the printer | `moonraker_file_upload` result plus `moonraker_file_verify` with `verified: true` |
| Ready to print | `moonraker_print_preflight` with no blocking reasons |
| Approved | the approval id/phrase from the prepare response, decided by a human |

If the evidence is absent, the stage did not happen. Say so.

## Do not improvise around a refusal

When a tool refuses, relay the refusal and its reason. Do not rephrase the
call, flip a policy flag, edit a config, or search for another tool that
happens to do the same thing. In particular:

- no hand-written or hand-edited G-code;
- no hand-typed or reconstructed base64 — use a real encoder, or ask the user
  for the encoded bytes;
- no invented "upload" or "verify" tool when `moonraker_file_upload` /
  `moonraker_file_verify` are unavailable;
- no raw Moonraker HTTP endpoint as a quiet substitute for them;
- no direct filesystem copy into the gcodes root unless the user explicitly
  chooses that fallback after being told the upload tool is unavailable;
- no self-approved confirmation or invented approval phrase.

When in doubt, stop and ask.
